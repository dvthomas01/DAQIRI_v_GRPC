### gRPC vs gRPC-Direct (one-liner)
Same application code, different transport underneath. Standard gRPC uses a TCP
kernel socket (serialize + kernel round-trip + multiple copies, ~1,000 us echo).
gRPC-Direct swaps the transport for shared memory / RDMA / low-latency TCP (data
placed once in a shared buffer, kernel bypassed). "Same code, faster pipe."

### Phase 1 (from README / LONGTERM_CONTEXT.md)
- Standard gRPC TCP baseline: ~929-1086 us echo p50 (call it ~1,000), 1.78 GB/s streaming
- gRPC-Direct shmem: **3.3 us** echo (281x faster), **23.59 GB/s** streaming (3.9x)
- gRPC-Direct TCP-LL: 21.2 us (44x)
- gRPC-Direct RDMA: 36.8 us (29x), 5.775 GB/s
- **The "tie with DAQiri on throughput" is RETRACTED. Do not present it.** The two figures were
  5.775 GB/s for gRPC-Direct and ~5.785 for DAQiri, quoted as a sub-1% tie. 5.785 GB/s is
  5518 MiB/s, and Gate 3 later measured this fabric at exactly 5518.37 MiB/s **with the RoCE
  MTU misconfigured at 1024**. Both arms were sitting on the same wall, and the wall was a
  misconfiguration rather than the hardware. A tie against a shared artificial ceiling is not
  evidence that the two transports perform alike. With the MTU at 4096 the same fabric does
  5843.23 MiB/s = **6.127 GB/s = 98.0% of the 6.25 GB/s line rate** (handoff 7p, Gate 3).
  Neither original figure's construction was ever written down and their per-message data is
  gone, so they cannot be rescued by reanalysis; they have to be re-measured.
- What is safe to say instead: **gRPC-Direct RDMA runs at 98% of line rate on a correctly
  configured fabric, and there is nothing left to win in the wire.** That is a stronger claim
  than the tie was, and it does not depend on a DAQiri number at all.
- **Same-host native floor (localhost): 2.78 us** (native Rust echo) — shmem 3.3 us is at this floor
- shmem/TCP-LL/standard-gRPC = SAME-HOST (localhost); RDMA = CROSS-MACHINE
- The 1.78 and 23.59 GB/s figures also have no recorded construction. They are not affected by
  the link-ceiling argument (shmem has no link), but if anyone challenges them there is nothing

# 10. TECHNICAL CONTEXT — writing code for open issues (e.g. the 128 KB DAQiri drop)

This section makes the handoff self-sufficient for CODE work. For the fullest detail,
also read the root `handoff.md` and `/memories/repo/grpc-zero-copy.md`.

## 10.1 The two pipelines (what the code does)

**Pipeline A (DAQiri):** `daqiri/bench_daqiri_pipeline.cc`
- Synthetic signal (`common/signal_gen.*`, 3 sine waves 500/1200/2500 Hz + noise) is
  copied into a DAQiri TX buffer and sent over a **TCP loopback socket engine**
  (`stream_type: "socket"`, `127.0.0.1`), then received, run through cuFFT, and logged.
- Threads: `tx_worker` (pinned `TX_CPU=11`) and `rx_pipeline_worker` (pinned `RX_CPU=9`).
- Modes: default = copy (H->D `cudaMemcpy`); `--zero-copy` = coherent in-place FFT via
  `cudaHostRegister` + device pointer (GB10 unified memory, host VA == device VA).
- Flags (parsed in `main()`, ~line 388): `--yaml <path>` `--bufsize <samples>`
  `--n-buffers <N>` `--warmup <N>` `--zero-copy` `--pace-us <us>` (TX sleeps this long
  after each `send_tx_burst`; 0 = unpaced).
- Constants (~line 54): `SERVER_ADDR 127.0.0.1`, `SERVER_PORT 7778`, `CLIENT_ADDR 127.0.0.1`.
- Output: per-buffer CSV with columns `e2e_latency_us,transfer_latency_us,fft_exec_us,`
  `samples_per_sec,buffers_per_sec,mb_per_sec,cpu_util_pct,gpu_util_pct,`
  `buffer_size_samples,dropped_buffers,wire_latency_us`. Delivered-row count = buffers
  the RX actually processed.

**Pipeline B (gRPC-Direct):** `grpc_direct/bench_grpc_server.cc` + `bench_grpc_client.cc`
- Same idea over the gRPC-Direct transport (shmem / TCP framing). Copy mode adds a host
  staging `memcpy`; ZC mode does a D2D-realign (wire payload align16=6 always needs it).
- Server logs `wire_latency_us`. Client `--pace-us` (default 400; 0 = unpaced -> STALLS).

## 10.2 Config that matters for the 128 KB drop

`daqiri/config_pipeline.yaml` (socket loopback, port 7778):
- `MEM_TX` / `MEM_RX`: `num_bufs: 4096`, `buf_size: 131136` (covers 32768 samples x 4 B
  = 131072 B, so the buffer is big enough — the drop is NOT a too-small-buffer issue).
- `socket_config.max_payload_size: 131136`.
- **`srv_rx_q` has `cpu_core: 9`** and **`rx_pipeline_worker` pins to `RX_CPU = 9`**.

## 10.3 The open issue: DAQiri drops buffers at 128 KB (32768 samples)

**Symptom (measured, airtight sweep, N=1000):** at 128 KB DAQiri delivers only ~124
(copy) / ~240 (zerocopy) of ~900-1000 rows; gRPC delivers ~971-973. At 16/32/64 KB
DAQiri delivers full. So the loss is specific to the largest payload on DAQiri's
**TCP-loopback socket engine**. Per-buffer p50 latency of the buffers that DO arrive is
still valid; only throughput/delivery at 128 KB is affected (footnoted on the figures).

**Leading hypothesis (NEW, strong, testable) — core contention:** the DAQiri socket
engine's receive queue `srv_rx_q` runs on `cpu_core: 9`, and the CUDA pipeline worker
(`rx_pipeline_worker`) is ALSO pinned to core 9 (`RX_CPU = 9`). At 128 KB the per-buffer
FFT + H->D takes longer, so the pipeline thread holds core 9 longer, starving the socket
engine's drain loop -> the kernel TCP loopback receive buffer overflows and drops at the
largest payload only. Smaller payloads finish fast enough that the socket keeps draining.

**Other hypotheses to rule in/out:**
- Kernel loopback socket buffer limit (`net.core.rmem_max` / `SO_RCVBUF`) saturating at
  128 KB bursts (needs sysctl inspection; sudo may be blocked, see constraints).
- TX outrunning RX: `tx_worker` retries `send_tx_burst` on failure but never blocks on
  RX progress; at 128 KB the RX ring (`num_bufs: 4096`) may fill.
- `batch_size: 1` on the RX queue: one syscall per 128 KB payload — no batching headroom.

## 10.4 Concrete diagnostic + fix plan (code-level)

Do these in order; each is a small, testable change.

1. **Instrument send-vs-receive to localize the loss.** In `bench_daqiri_pipeline.cc`
   add counters: TX successful `send_tx_burst`, TX failed sends (the `else` branch that
   `free_tx_metadata`s ~line 141-146), RX bursts received, RX sub-buffers processed.
   Print all four in `print_stats` at exit. If TX-sent == n_buffers but RX-received is
   short, the loss is in the socket/RX path (supports the contention/socket-buffer
   hypotheses). Diagnostic run command (Spark, when reachable):
   `taskset -c 9,11 build/daqiri/bench_daqiri_pipeline --yaml daqiri/config_pipeline.yaml`
   `--bufsize 32768 --n-buffers 1000 --warmup 100 --pace-us 400 --out /tmp/diag_32768_zc.csv --zero-copy`

2. **Test the core-contention hypothesis (cheapest, most likely fix).** Move the CUDA
   pipeline worker off the socket-engine core. Either (a) change `RX_CPU` from 9 to a
   free core (e.g. 13) in `bench_daqiri_pipeline.cc` and re-`taskset` accordingly, or
   (b) change `srv_rx_q.cpu_core` in `config_pipeline.yaml` to a different core from the
   pipeline worker. Re-run the 128 KB case; if delivery jumps toward full, contention
   was the cause.

3. **If TX outruns RX:** add backpressure — have `tx_worker` pace based on RX progress
   (e.g. cap `tx_count - rx_count` outstanding) instead of a fixed `--pace-us`, or raise
   `--pace-us` only at 128 KB and confirm delivery recovers (a pace sweep at 128 KB).

4. **If it is a kernel socket-buffer limit:** inspect `sysctl net.core.rmem_max` /
   `net.ipv4.tcp_rmem`. Raising them needs sudo (may be blocked). If so, document as a
   transport-level limit of the TCP-loopback engine (the flagship NIC-to-GPU RDMA path
   would not hit this) — this is how slide 8 currently frames it.

5. **Validate the fix** by re-running the airtight sweep at 128 KB (both modes) and
   confirming DAQiri delivery approaches gRPC's, without regressing per-buffer latency.
   Then update slide 8 (open item -> resolved) and the figures via
   `python scripts\make_deck_figs.py`.
